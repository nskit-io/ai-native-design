# AI-Native Design

**AI が理解し、変更し、出荷できるようにコードを構造化する設計原則。**

> コード構造を、人間の読みやすさではなく、AI が実際にコードを処理・修正する方法に合わせて最適化したら?

> 文脈: これらの原則は [**NSKit**](https://github.com/nskit-io/nskit-io) を支えています — *型にはまっているから、無限に組み合わせられる*。本番運用のウェブアプリ・プラットフォームで、原則を「実際に動くサービス」へと結実させます。AI ビジュアル生成ツール(Claude Design、v0、Lovable)は別レイヤー — 彼らはモックアップを作り、NSKit は AI-Native Design を **実際に動くコード** に適用します。

---

## なぜ必要か

React、Vue、Angular のような現代フレームワークは **Human Developer Experience** のために見事に設計されています。モジュール性、型安全、再利用性、関心の分離。人間が主要な書き手なら、これらは正しい目標です。

しかし AI が主要な協業者になると — コードを読み、文脈を理解し、変更し、機能を出荷するとき — 最適化すべき対象が変わります。**AI-Native Design** は「どんな構造なら AI が最も正確かつ効率的に動けるか?」という問いから生まれたアーキテクチャ原則のセットです。

これはフレームワークでもライブラリでもなく、**本番システムでのベンチマークに裏付けられた設計哲学**です。

---

## 中核の対立

| 関心事 | Human DX 最適化 | AI DX 最適化 |
|---|---|---|
| **ファイル構造** | 明確な import を持つ小さなモジュール | すべてインラインの Self-Contained ファイル |
| **依存関係** | 抽象化、再利用、共有 | 最小化。すべての import は AI が辿るべき文脈 |
| **型システム** | 安全と文書化のためのリッチな型 | 型より規約、契約よりパターン |
| **ファイルサイズ** | 可能な限り小さく(SRP) | 500〜800行が最適(文脈ウィンドウ効率) |
| **ビルドプロセス** | 最適化のため Webpack/Vite/esbuild | なし。エラーのカテゴリごと排除 |
| **状態管理** | 集中ストア(Redux、Pinia) | ファイルスコープ。共有可変状態なし |

どちらが「優れている」わけではなく、**異なる制約を解いている** のです。AI がコードの 80%以上 を書くとき最も重要な制約は: **この1ファイルを AI がどれだけ正確に理解・修正できるか**。

---

## 6つの原則

1. **Self-Contained Files** — HTML + CSS + JS を1ファイルに。import を辿らなくて済む。
2. **500〜800 行のスイートスポット** — 文脈ウィンドウに最適化。NSKit フレームワーク実測: JS 22 ファイル・計 11,850 行・平均 539 行。
3. **No Build Process** — バンドラ・トランスパイル起因のエラーをカテゴリごと排除。
4. **Convention over Configuration** — 予測可能なパターンが設定より AI を助ける。
5. **設計目標としてのトークン効率** — AI が読む1行ごとにトークンがかかる。
6. **Parallel AI Sessions** — 共有可変状態なし。並列 AI セッションで衝突ゼロ。

各原則のコード例と根拠は [英語版 README](README.md) 参照。

## トークン効率(推定)

カードコンポーネントのクリックハンドラを1つ変更する場合の推定値:

| 比較対象 | 1 変更あたりのトークン |
|---|---|
| React(モジュール分割) | ~25,000(中央推定値) |
| **AI-Native(Self-Contained)** | **~800** |

**約 31 倍の効率**。推定方法と前提は [benchmarks/token-comparison.md](benchmarks/token-comparison.md) を参照。実際の値はプロジェクトによって異なります。

## NSKit との関係

| 層 | 関係 |
|---|---|
| **AI-Native Design** | 設計原則(本リポジトリ) |
| **NSKit** | これらの原則を適用した本番フレームワーク |
| **NSKit Template Mixing** | 原則に従う統一構造だからこそ、テンプレートの無限組み合わせが可能 |

原則は普遍的 — あなた自身のプロジェクトに適用できます。NSKit はその参照実装の1つです。
